1. Сильні сторони

ДОБРЕГоловний інваріант дотримано на рівні коду

Сигнали безпеки формуються детерміновано на FactStore (L1/L2a), а L2b лише витягує факти без висновків. Це операціоналізований людський нагляд — відповідь на EU AI Act ст. 14 ще до MVP.

l3_router.route() ескалює незалежно від впевненості витягу, якщо є major/critical-сигнал — правильна семантика: сигнал на факт-сторі достовірний завжди.

ДОБРЕЧіткі контракти між шарами

Єдиний тип Signal(layer, kind, severity, confidence) повністю роз'єднує L3 від реалізацій L1 та L2a. Protocol Extractor дає clean-room підміну StubExtractor → MedGemmaExtractor без зміни конвеєра.

FHIR-вирівняні Pydantic-моделі з кодами LOINC/RxNorm/SNOMED закладають сумісність з eHealth без переписування.

ДОБРЕДва узгоджених сховища з ідемпотентністю

FactStore — ідемпотентний за obs_id: повторний ingest того ж документа не дублює факти. KnowledgeGraph зберігає провенанс-ребра (derived_from), що дозволяє кожній Q&A-відповіді посилатися на документ-джерело.

ДОБРЕLiveMedCard — єдине джерело істини

pipeline.LiveMedCard зберігає канонічні FHIR-ресурси; FactStore і KnowledgeGraph — похідні проєкції. Це дає симетричний snapshot/from_snapshot, FHIR Bundle export/import і аудит L3 без додаткової синхронізації.

ДОБРЕTyped reference models + sex-aware ranges

refmodels.py + reference.range_for(loinc, sex) — референсні межі з урахуванням статі (напр. креатинін ♀ ≤ 90 vs ♂ ≤ 106). Це не косметика: тест test_female_creatinine_breach_uses_sex_range ловить клінічно значущий кейс.

2. Знайдені проблеми

КРИТИЧНОГлобальний mutable стан у API

У api.py є глобальна змінна _card: LiveMedCard, яку reset та import_bundle перезаписують через global _card. При будь-якій багатопотоковості (навіть кілька вкладок браузера) — race condition.

Ризик: пацієнт A бачить дані пацієнта B після reset; аудит змішується.

# api.py — зараз
_card = LiveMedCard(_new_patient())  # module-level singleton

@app.post("/reset")
def reset():
    global _card              # ← небезпечно при concurrency
    _card = LiveMedCard(_new_patient())

Рекомендація: помістити _card у FastAPI dependency або використати asyncio.Lock; для prod — виокремити стан у repository-шар з per-patient ізоляцією.

КРИТИЧНОНемає автентифікації та ізоляції пацієнтів

Будь-хто, хто знає URL, бачить медичні дані, може скинути картку або імпортувати довільний Bundle. Для хакатону прийнятно, для будь-якого реального розгортання — GDPR / Закон про персональні дані.

Рекомендація (мін.): JWT або OAuth2 Bearer токен через fastapi.security; кожен пацієнт — окремий LiveMedCard з ізольованим сховищем.

ВАЖЛИВОreference.py — відсутність кешу на рівні об'єктів

_raw(name) кешовано через @lru_cache, але load_interactions(), load_dose_limits(), load_vocab() щоразу будують нові Pydantic-об'єкти:

def load_interactions() -> list[Interaction]:
    return [Interaction(**p) for p in _raw("interactions.json")["pairs"]]
# ↑ викликається кожного ingest() → нові об'єкти кожного разу

При великих БД (тисячі взаємодій) це помітне зайве навантаження. L1 перебудовує pair_map при кожному виклику check_interactions().

Рекомендація: додати @lru_cache або модуль-рівневий singleton на самі load_* функції; pair_map в L1 — модуль-рівнева константа.

ВАЖЛИВОl2b_extractor — confidence захардкоджений як 0.95

StubExtractor виставляє confidence=0.95 для кожного витягнутого факту, незалежно від якості. Це магічна константа без тесту на граничний випадок.

provenance=Provenance(
    source_doc_id=doc.id,
    extracted_by="StubExtractor",
    confidence=0.95,   # ← завжди 0.95, навіть для нечіткого матчингу
)

Рекомендація: винести в config.py як STUB_CONFIDENCE = 0.95; при переході на реальний екстрактор — confidence залежить від модельної впевненості токена.

ВАЖЛИВОQA.ask() — keyword matching без нормалізації

Маршрутизація питань у qa.py — проста перевірка kw in q по _KEYWORD_TO_LOINC. Перефразування, помилки друку, синоніми — мовчазна порожня відповідь.

_KEYWORD_TO_LOINC = {
    "нирк": "2160-0",
    "креатинін": "2160-0",
    ...
}
# "Яка функція нирок?" → спрацює; "Нирки в порядку?" → спрацює;
# "Чи норм філтрація?" → не спрацює → "Не вдалося зіставити..."

Рекомендація: додати fuzzy-matching або просту TF-IDF схожість для fallback; або перейти на embedding-based retrieval при підключенні MedGemma.

ВАЖЛИВОFactStore.series() — O(n) кожного виклику

series(loinc) лінійно проходить увесь _facts при кожному зверненні. Метод current_signals() викликається на кожному ingest та кожному GET /state — і всередині двічі обходить весь стор (trend + breach).

Рекомендація: зберігати індекс dict[loinc, list[KVTFact]] поруч із _facts; тоді series() — O(1) lookup + O(k log k) сортування (k — кількість вимірів одного показника).

ВАЖЛИВОObservation ID — не стабільний між запусками

StubExtractor генерує id як f"{doc.id}-obs-{i}" де i — порядок знахідок у конкретному документі. Якщо словник vocab.json зміниться або порядок матчингу зміниться — id зміниться, і FactStore втратить ідемпотентність при завантаженні snapshot зі старими ids.

Рекомендація: id = детермінований хеш від (doc.id, loinc, effectiveDateTime) — стабільний і колізієстійкий.

ВАЖЛИВОАудит: _audit — mutable dict без схеми

_audit — список dict без типізації. Немає гарантії структури між версіями; from_snapshot відновлює їх «як є» без валідації.

Рекомендація: визначити AuditEntry(BaseModel) в dto.py; серіалізація через model_dump(), десеріалізація через AuditEntry(**a).

НОТАТКАСтатичні файли та data/*.json не входять у wheel

pyproject.toml пакує лише Python-модулі. При pip install livemedcard бракуватиме static/index.html і всіх data/*.json.

# pyproject.toml — додати:
[tool.hatch.build.targets.wheel]
packages = ["livemedcard"]
artifacts = ["livemedcard/static", "livemedcard/data"]
НОТАТКАНемає CI / linter / type check

Репозиторій має .github/-директорію, але немає workflow для автоматичного запуску pytest, ruff і mypy/pyright на кожному PR. Тести написані — автоматизація відсутня.

Рекомендація: мінімальний .github/workflows/ci.yml на uv run --extra dev pytest -q + ruff check livemedcard/.

import hashlib

def _obs_id(doc_id: str, loinc: str, ts: str) -> str:
    key = f"{doc_id}|{loinc}|{ts}"
    return "obs-" + hashlib.sha1(key.encode()).hexdigest()[:12]

# використання:

4.2 Індекс у FactStore (stores.py)

class FactStore:
    def __init__(self) -> None:
        self._by_loinc: dict[str, list[KVTFact]] = {}
        self._seen_ids: set[str] = set()

    def add_observation(self, o: Observation) -> Optional[KVTFact]:
        if o.id in self._seen_ids:
            return None
        fact = observation_to_kvt(o)
        if fact is not None:
            self._by_loinc.setdefault(fact.loinc or "", []).append(fact)
            self._seen_ids.add(o.id)
        return fact

    def series(self, loinc: str) -> list[KVTFact]:
        return sorted(self._by_loinc.get(loinc, []), key=lambda f: f.ts)

    def loincs(self) -> list[str]:
        return list(self._by_loinc)

6. Що НЕ треба змінювати

  • Головний інваріант TRACE (детерм. сигнали на FactStore, L2b лише витяг) — архітектурна основа, зберігати при будь-яких змінах.
  • Extractor Protocol — чистий інтерфейс для підміни на MedGemma без торкання конвеєра.
  • LiveMedCard як єдине джерело істини з snapshot/from_snapshot — симетрична серіалізація, потрібно лише додати AuditEntry-типізацію.
  • FHIR-вирівняні Pydantic моделі — закладають сумісність з eHealth; розширювати, не замінювати.
  • Детермінований StubExtractor — правильний дефолт для MVP; залишити як fallback і regression fixture навіть після MedGemma.
  • local-first JSON persistence — правильна відповідь на «медичні дані не залишають пристрій»; SQLite — природна наступна сходинка, не Postgres.

7. Підсумок

LiveMedCard — технічно зрілий MVP для 48 год. хакатону. Архітектурний каркас TRACE реалізовано правильно: межа між детермінованим та генеративним збережена в коді, а не лише в документації. Основні ризики — не в архітектурі, а в production-readiness: глобальний стан, відсутня автентифікація, нестабільні ID ресурсів.

Пріоритет P0 (~2–3 год. роботи): прибрати global _card, стабілізувати ID, типізувати аудит, додати CI. Це перетворює демонстратор на код, який можна показувати інвесторам без застережень.

Пріоритет P1 (~1–2 тижні): OCR pipeline, real MedGemma extractor, per-patient isolation — перетворює прототип на придатний до пілоту продукт без зміни архітектури.
