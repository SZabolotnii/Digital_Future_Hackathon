# LiveMedCard — підсумковий технічний review

**Дата:** 11 липня 2026  
**Статус:** сильний hackathon-MVP; не готовий для обробки реальних медичних даних без описаних нижче змін.

## Висновок

LiveMedCard має переконливу архітектурну основу: L2b/LLM лише витягує кандидатні факти, тоді як L1 (взаємодії та дози) і L2a (тренди та референсні межі) рахуються детерміновано над FactStore. Провенанс, FHIR-експорт, bilingual Q&A, per-session demo та відтворюваний OCR benchmark помітно підсилюють продуктову й технічну достовірність проєкту.

Локальні перевірки успішні:

- `uv run --extra dev pytest -q` — **125 passed**;
- `uv run --extra dev ruff check livemedcard tests` — без зауважень;
- публічне демо `https://docua-livemedcard.hf.space/` відповідає на `GET /` і віддає актуальну SPA.

## Сильні сторони

1. **Правильно встановлена safety-межа.** Модель не породжує L1/L2a-сигнали й не приймає рішення L3; це важливе розділення між extraction та clinical safety.
2. **Провенанс як інваріант.** Факт без `source_doc_id` відхиляється ще на межі ingest; span-level прив'язка робить Q&A перевірюваним.
3. **Практичне демо.** Per-session стан усуває змішування даних між відвідувачами, а записаний NuExtract-кліп прибирає ризик cloud latency під час пітчу.
4. **Якісний synthetic demo asset.** `pitch/clip/lab_report_en.jpg` візуально професійний і явно містить синтетичні дані.
5. **Чесний OCR benchmark.** Документація прямо обмежує висновки набором із п'яти документів і не подає його як клінічну валідацію.

## Критичні зауваження

### 1. Валідація одиниць має передувати L2a-сигналам

`livemedcard/layers/l2a_trends.py` порівнює числове значення з референсним діапазоном без перевірки сумісності `unit`. Наприклад, glucose у `mg/dL`, якщо її буде закодовано як LOINC `2345-7`, потенційно порівнюється з межами `mmol/L` (`3.9–6.1`). Це може спричинити хибні сигнали.

**Рекомендація:** додати UCUM-style canonical units, allowlist конверсій та `unit_mismatch`/manual-review шлях. До успішної нормалізації L2a не повинен формувати range breach або trend для такого ряду.

### 2. Confidence LLM-витягу зараз не калібрований

`NuExtractExtractor`, `LoraStage2Extractor` і `OcrLabExtractor` повертають `STUB_CONFIDENCE` (`0.95`) просто коли існує хоча б один факт. Отже, L3 може трактувати неповний або помилковий OCR як високовпевнений.

**Рекомендація:** окремий стан `unknown/unverified`; фото-OCR без валідованої confidence маршрутизувати на review. Надалі оцінювати confidence по schema validity, unit/code consistency, coverage expectation і незалежному quality model.

### 3. Public UI не дає достатньо явного cloud-consent

Docker-профіль вмикає `LMC_IMAGE_OCR=ocrlab`: фото передається до зовнішнього ZeroGPU OCR Lab. Водночас у trust-блоці UI є твердження «Без хмарної LLM», а користувач бачить переважно повідомлення про очікування до 90 секунд.

**Рекомендація:** перед upload показувати обов'язкове підтвердження, що файл залишить пристрій; прямо заборонити PHI/PII в публічному Space; динамічно змінювати privacy-indicator залежно від активного OCR backend.

### 4. Не перебільшувати гарантію детермінізму

Формула «AI помилився — interaction не буде пропущено» некоректна: якщо LLM не витягла один з препаратів, L1 не має повної пари фактів для детермінованої перевірки.

**Рекомендоване формулювання:** «LLM не ухвалює safety-рішень і не може згенерувати interaction. Після вилучення фактів взаємодії та дози перевіряються детерміновано; неповне або невпевнене вилучення потребує людської перевірки».

### 5. Додати E2E-тест нового англомовного документа

Поточний keyword→LOINC міст не гарантує точного розпізнання `Fasting glucose` і `Hemoglobin A1c (HbA1c)`: він орієнтується на точніші ключі `glucose` і `hba1c`.

**Рекомендація:** додати fixture markdown/KVT для `lab_report_en`, E2E-тест чотирьох Observation, перевірку LOINC, unit і очікуваних L2a-сигналів.

## Важливі покращення наступними

1. Unit validation/conversion перед L2a.
2. Calibrated або explicit-unknown extraction confidence.
3. Cloud-consent і коректний privacy UI.
4. De-identified UA/EN golden corpus у CI: Stage 1 → KVT → Observation → signals.
5. Реальний PDF intake або звуження продуктового твердження до тексту та зображень.
6. Оновити згадки про кількість тестів у документації з 111 до 125.

## Перевірка через Chrome MCP

Проведено діагностику Chrome: браузер запущений, ChatGPT Chrome Extension увімкнений у профілі `Default`, native host manifest коректний. Після відкриття нового вікна Chrome browser-connector усе одно не виявив доступного extension backend, тому UI-flow у Chrome MCP виконати не вдалося. Для відновлення інтеграції слід перевстановити Chrome plugin через UI Codex/ChatGPT і повторити перевірку.
