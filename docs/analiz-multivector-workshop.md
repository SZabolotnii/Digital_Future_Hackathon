# Multi-Vector Retrieval Workshop vs. темпоральний граф LiveMedCard

> Аналіз домашнього завдання `05_homework.ipynb` з
> [sokoloff/multi-vector-workshop](https://github.com/sokoloff/multi-vector-workshop):
> чи розв'язується воно нашим темпоральним графом і де реальний перетин із проєктом.
> Дата: 2026-07-23.

## Короткий висновок

Темпоральним графом це домашнє **не розв'язується** — і не через брак зусиль, а тому
що це задача іншого класу. Проте перетин із LiveMedCard є, і він не там, де здається:
інструменти воркшопу лягають не на граф, а на **retrieval-шар і OCR-конвеєр** картки.

Порада стисло: **здавати домашнє як IR-задачу (без графа), а з воркшопу винести в
проєкт не розв'язок, а три техніки** — ColPali-ретрив, MUVERA-two-stage і
byte-normalized eval.

## Що це насправді за завдання

Це не про графи знань і не про час. Це **бенчмарк multi-vector retrieval** — пошуку по
сторінках документів (шість 10-K звітів, підвибірка ViDoRe V3 Finance) через
late-interaction моделі. Завдання — відтворити «драбину якість-проти-вартості» з п'яти
конфігів:

1. **текстовий baseline** — parsed markdown сторінки → один щільний вектор (MiniLM),
   single-vector COSINE у Qdrant;
2. **повний ColPali/ColSmol** — патч-мультивектори, native MaxSim у Qdrant (стеля
   якості й вартості);
3. **pooling** патчів (ієрархічний, фактори ×2 та ×4);
4. **бінарна квантизація** (1 біт/вимір, 16× проти fp16);
5. **MUVERA two-stage** — FDE-prefetch (HNSW-able) → MaxSim-rerank, глибини 10 і 50.

Стек: `Qdrant (:memory:)` для зберігання/пошуку, `ranx` для оцінки (NDCG@5, Recall@10,
MRR + парна значущість), `colpali-engine` для моделей. Метрики нормалізуються на GB —
«більша модель мусить *заробити* свої байти». Технічно там 6 TODO, і **до кожного вже є
Hint зі готовим рішенням на ~5 рядків**; реальний дедлайверабл — не код, а аналітичний
write-up «яку конфігурацію я б задеплоїв і чому».

## Чому темпоральний граф тут не працює

Наш темпоральний граф (`livemedcard/temporal.py`) моделює **еволюцію сутностей у часі**:
першу появу, епізоди, інтервали активності, топологію мультиморбідності. Для цього
потрібні дві речі, яких у цьому завданні **немає взагалі**:

- **немає осі часу** — корпус статичний, 500 сторінок без хронології; запит «коли вперше
  з'явилось» тут беззмістовний;
- **немає сутностей і зв'язків** для витягу — задача оперує сторінками як непрозорими
  векторами, а не як фактами в графі.

Це чистий **information retrieval eval**: якість ранжування проти вартості зберігання.
Прикрутити сюди граф — це підганяти інструмент під неспоріднену задачу; він не додасть ані
NDCG, ані економії байтів, лише плутанину.

## Де перетин справжній

Хибно було б сказати «ці інструменти нам ні до чого». Навпаки — вони лягають на
LiveMedCard напряму, просто через два інші вузли, не через граф.

### 1. Наш `retrieval.py` — це буквально config #1 з домашнього

Grounded-Q&A картки робить single-dense пошук по free-text іпостасі (лексика + опційно
косинус embeddings через `llm_client.embeddings`). Це найслабша сходинка драбини
воркшопу. ColPali-стиль (late interaction, MaxSim) — готовий апґрейд recall-у Q&A, якщо
знадобиться точніший ретрив по довгих виписках. Причому наш `Embedder`-протокол уже
абстрагує бекенд, тож заміна на Qdrant-MaxSim не ламає решту конвеєра.

### 2. ColPali б'є прямо в наш OCR-больовий вузол

Поточний конвеєр: фото → OCR/vision → текст → витяг. ColPali — це **retrieval без OCR**:
сторінка-зображення кодується в патч-вектори напряму. Для медичних документів із
таблицями, штампами, рукописом (де OCR найбільше сипле) це концептуально сильніший шлях
до «знайти релевантну сторінку», ніж наш text-first. **Важливо:** це для ретриву й
навігації, НЕ для сигналів безпеки — там межа детермінізму лишається (L2b не робить
висновків про безпеку).

### 3. MUVERA + бінарна квантизація — це наша local-first математика

Уся драбина воркшопу про «якість, нормалізована на GB» — це **той самий хребет, що й
Computational Parsimony Ratio (CPR) у TRACE**: не платити за обчислення, яких задача не
вимагає. Наш публічний доказ (6.4 ГБ RSS, ~16 tok/s, CPU-only) — рівно та вісь
«якість/вартість», яку домашнє вчить міряти через `ranx`. Квантизація й MUVERA — прямі
важелі, щоб мультивекторний ретрив узагалі влазив у on-device бюджет.

## Вердикт

Домашнє і наш темпоральний граф — **дві різні площини**:

| | Домашнє (multi-vector workshop) | Темпоральний граф LiveMedCard |
|---|---|---|
| Питання | як дешево й точно **знайти** сторінку | як показати, що **змінилось у часі** |
| Клас задачі | information retrieval + benchmarking | моделювання еволюції сутностей |
| Дані | статичний корпус сторінок-векторів | датовані факти з провенансом |
| Оцінка | NDCG@5 / Recall@10 / MRR (ranx) | описові метрики топології, сигнали L2a |

Граф домашнє не розв'язує і не має. Але як система LiveMedCard отримує з воркшопу
**retrieval-шар, якого їй бракує**: ColPali замість OCR-first для навігації по
документах, MUVERA/квантизацію під on-device бюджет, а методологію «якість-на-GB через
ranx» — як операціоналізацію CPR у наш bench.

## Наступний крок (опційно)

Переписати `retrieval.py` на Qdrant-MaxSim бекенд за наявним `Embedder`-протоколом, щоб
семантичний ретрив картки став опційно late-interaction без ламання решти конвеєра.
Оцінити по-воркшопному: byte-normalized recall на де-ідентифікованих виписках.
